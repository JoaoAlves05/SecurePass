# Signed authorization prototype — specification and review gate

Status: internal prototype for review and regression tests. Not activated in the extension, not a release protocol and not an independently reviewed security claim. Existing vault-v2 encryption remains authoritative; no stored vault is migrated by these modules.

Authorization uses an independent ECDSA P-256/SHA-256 administrative key, separate from WebAuthn and ordinary writer keys. A state contains kind/version, vaultId, keyEpoch, revision, previous state digest, administrative SPKI and a sorted unique list of active device IDs/SPKIs. Limits: 128 devices and 256 states per supplied chain. Private keys never appear in a state. Signatures use Web Crypto's 64-byte IEEE-P1363 representation.

The signed message is UTF-8 JSON of a fixed ordered tuple prefixed by `SecurePass:authorization:1`. The state digest is SHA-256 of this tuple, excluding the signature to avoid signature-malleability changing ancestry. Genesis is self-signed, but accepted only against an independently supplied root fingerprint (SHA-256 of its administrative SPKI) and expected vault ID. Every subsequent state references the previous digest and is signed by the previous administrative key. Administrative-key replacement is therefore authenticated by its predecessor. Concurrent successors are separate heads, never ordered by clocks or counters.

Chain verification can require an already-known final state digest. Supplying an earlier valid state instead fails. Without an independent final checkpoint, bootstrap freshness remains explicitly unproven; a root fingerprint alone cannot establish recency. Persisting/advancing the trusted checkpoint, enrollment UI, concurrent administrative resolution, and recovery/rotation transitions remain required before activation.

A signed revision wraps a strictly validated existing vault-v2 encrypted record with author device ID and exact authorization digest. Its signature binds a fixed ordered tuple with domain `SecurePass:revision:1`. The record vault/epoch must match the verified authorization state; the author must currently be active. Verification against the current state rejects old authorizations and revoked authors. Historical import requires a separate authenticated history policy, not weakening the live-write check.

Only canonical JSON emitted by the serializer is accepted by the publication validator, rejecting ambiguous encodings, duplicate keys, unknown cleartext fields and unsupported formats. The verifier uses immutable state objects issued by successful chain verification; callers cannot substitute a plain unverified object. Reverify after worker restart. Existing ciphertext bounds and schema validation apply before expensive signature operations.

Outstanding review: multi-device nonce budget/per-writer key derivation, new encryption format, maximum ancestry, administrative enrollment/recovery proofs, private-key wrapping/storage/lifetime, durable trusted checkpoints and rollback handling, history verification, concurrent rotation and migration. This prototype does not satisfy those release gates and must not be used as a substitute for them.

## Key protection and trusted checkpoint implementation

`signingKeyProtection.js` protects a PKCS8 administrative key using a bounded PBKDF2 master-derived AES-GCM key, salt and authenticated vault/epoch/role/key identity. A device key can instead be protected by the 256-bit content key, permitting ordinary writing after local biometric unlock. The content key cannot unwrap the administrative envelope. Plain key buffers are cleared best-effort; returned signing CryptoKeys are nonextractable. This does not guarantee physical erasure in JavaScript or remove the need for an authenticated administrative caller and key lifecycle.

`authorizationStore.js` persists the pinned root, chain and known head in the vault IndexedDB database. Loading reverifies the signatures and expected head; advancing requires the existing head in the supplied verified ancestry and an atomic compare-and-write. Concurrent administrative branches cannot silently overwrite each other. Enrollment/pinning is an internal API requiring independent confirmation by its future management caller; it has no public message route.

These checkpoints protect against a remote provider serving an old branch after a local newer checkpoint is known. They do not establish freshness after loss/restoration of all local trusted state, or resist an attacker replacing the entire local extension database/root pin. Protecting and integrating trust metadata with the master/content epoch remains part of the protocol review.

The `prepareSignedPublication` helper connects a signed packet to the atomic repository/outbox API and emulated Drive read-back acknowledgement. Prepared packets carry their authorization digest into the atomic commit. That transaction compares the persisted authorization head, and queued operations recheck the head before sending/failure updates/acknowledgement. Administrative changes invalidate old queued authority without deleting the local revision. The 2026-11-06 integration adds automatic normal-mutation signing for an internally enrolled writer, session/deadline checks, atomic local-restore suspension, account/token guards and worker scheduling behind a false production review predicate. Enrollment and administrative/rebase UI remain unavailable; these changes do not establish a reviewed release protocol. Persist the packet once per revision and reuse its exact bytes: ECDSA signatures are randomized, so recreating a packet is not an idempotent retry.

Primitive API reference: [W3C Web Cryptography](https://www.w3.org/TR/webcrypto/). This reference describes the primitives, not an endorsement or security proof of the SecurePass protocol.
